## Summary
This changeset introduces automated data retention, periodic purge scheduling, terminal token scrubbing, and consolidation of rate-limiting infrastructure by deprecating `LoginRateLimit` in favor of `RateLimit`. The overall architecture is strong, forward-thinking, and significantly reduces the cryptographic blast radius by scrubbing sensitive credentials upon consumption or terminal transitions. However, there are major concerns regarding false-positive session revocation under multi-worker deployments, session advisory lock compatibility with PgBouncer transaction pooling, and missing retention indexes for PostgreSQL.

## Major

### 🟠 Cross-worker refresh token replay false positives defeat concurrency grace window, `backend/app/services/session_service.py:345-368`
**Problem**: When a client refreshes a token on Worker A, Worker A rotates the refresh token and immediately commits the old nonce hash to `revoked_tokens` in the database. If a legitimate SPA client issues concurrent requests (e.g., across multiple browser tabs or rapid component mounting) and Request 2 reaches Worker B within the 15-second grace window, Worker B does not have Worker A's local in-memory `_rotated_tokens` dictionary. Worker B queries the database, finds `nonce_hash` in `revoked_tokens`, flags it as `TOKEN_REUSE_DETECTED`, and invokes `_revoke_session_family`, permanently destroying the user's active session family.
**Why it matters**: In multi-worker production environments (such as Gunicorn or horizontal scaling), legitimate users with multiple open tabs will intermittently and unpredictably be logged out during normal token refresh operations.
**Suggested fix**: Consider checking the `created_at` timestamp on the persisted `RevokedToken` record before treating it as an adversarial replay. If `(now - revoked_row.created_at) <= settings.REFRESH_GRACE_PERIOD_SECONDS`, treat the request within the grace window rather than immediately revoking the entire session family, or persist rotated token grace state into shared storage.

### 🟠 PostgreSQL session-level advisory locks are unsafe under PgBouncer transaction pooling, `backend/app/tasks/retention_purge.py:30-45`
**Problem**: `_try_acquire_advisory_lock` executes `pg_try_advisory_lock`, which is a PostgreSQL session-level advisory lock tied to the physical backend connection. The project connects to Supabase through port 6543, which enforces PgBouncer transaction pooling. In transaction pooling mode, because `run_auth_retention_purge` executes multiple commits across batches, subsequent queries and the final `_release_advisory_lock` can be routed to different backend database connections.
**Why it matters**: The advisory unlock can be dispatched to a different physical server connection than the one that acquired it, leaving the lock dangling on the original server connection until that connection is recycled, causing subsequent purge attempts on other workers to be indefinitely blocked.
**Suggested fix**: Use a transaction-scoped advisory lock (`pg_try_advisory_xact_lock`) for short single-transaction purges, or use a dedicated database row lock/heartbeat table (e.g. `cron_locks` with a timestamp and worker lease ID) that is safe across connection poolers.

### 🟠 Missing retention query indexes in PostgreSQL migration 0051, `backend/migrations/0051_auth_data_retention.postgres.sql:1-44`
**Problem**: While SQLite migration 0051 added a composite index `idx_otp_challenges_retention (created_at, status)`, PostgreSQL migration 0051 added indexes only for `revoked_tokens`. None of the retention purge indexes were added for PostgreSQL tables: `rate_limits` (`last_attempt_at, locked_until`), `login_otp_challenges` (`created_at, status`), `invitation_outbox` (`status, updated_at`), and `user_sessions` (`created_at`).
**Why it matters**: Every 6 hours, the retention scheduler will perform repeated sequential full-table scans across `rate_limits`, `login_otp_challenges`, `invitation_outbox`, and `user_sessions`. As these tables grow, purge jobs will cause CPU and I/O spikes in production PostgreSQL.
**Suggested fix**: Update `0051_auth_data_retention.postgres.sql` and `migrations.py` to create composite B-tree indexes matching the exact `WHERE` clauses used in `cleanup_expired_records`, `cleanup_expired_challenges`, `cleanup_invitation_tables`, and `cleanup_expired_user_sessions`.

## Minor

### 🟡 Unhandled `ValueError` crash potential on malformed `created_at` during logout, `backend/app/api/v1/endpoints/auth.py:235`
**Problem**: In `logout()`, `float(created_at) if created_at is not None else None` is evaluated outside the `try/except` block protecting `decrypt_payload`. If `created_at` in a decrypted cookie payload is non-numeric or corrupted, `float(created_at)` raises `ValueError`.
**Why it matters**: A malformed or corrupted session cookie will crash `POST /auth/logout` with an unhandled HTTP 500 error instead of clearing cookies and gracefully concluding the logout flow.
**Suggested fix**: Safely parse `float(created_at)` inside the `try/except` block where `payload.get("created_at")` is extracted, defaulting to `None` if casting fails.

### 🟡 Unscoped `locked_until <= now` resets attempt counters across unrelated records, `backend/app/services/auth_service.py:1298-1306`
**Problem**: In `reset_password()`, the rate-limit reset query contains `(RateLimit.locked_until <= now) | (...)`. Because `locked_until <= now` is evaluated across the entire `rate_limits` table without user scoping, completing a password reset clears attempts for all expired lockout rows on the server.
**Why it matters**: While expired lockouts are no longer active, resetting attempts to 0 across the entire table unintentionally wipes historical rate-limit metrics and counter progressions for unrelated users and IP addresses.
**Suggested fix**: Scope the `locked_until <= now` filter to the resetting user's email and combo identifiers rather than applying it globally.

### 🟡 Unbatched audit log purge and synchronous Supabase REST call in periodic scheduler, `backend/app/tasks/retention_purge.py:161-163`
**Problem**: `run_auth_retention_purge()` unconditionally calls `activity_log_service.cleanup_expired_logs(retention_days=180)`, which performs an unbatched DELETE and an external synchronous HTTP request to Supabase REST.
**Why it matters**: If hundreds of thousands of activity logs exist older than 180 days, an unbatched delete risks prolonged table locking. Additionally, network instability with Supabase REST can delay or fail the scheduled purge.
**Suggested fix**: Batch the local `AuditLog` deletion query and separate audit log maintenance from high-frequency auth credential cleanup.

## Nits

- ⚪ `backend/app/services/auth_service.py:1301`: `RateLimit.identifier.like(f"{norm_user_email}%")` does not escape SQL LIKE special characters (`_`, `%`), which may unintentionally match similar email strings where `_` is a wildcard.
- ⚪ `backend/app/core/config.py:73`: `OTP_AUDIT_RETENTION_DAYS` is retained for backwards compatibility; it should be annotated with a deprecation comment and planned for removal once callers migrate to `OTP_CHALLENGES_RETENTION_DAYS`.

## Strengths

- **Terminal Credential Scrubbing**: Excellent security hardening by proactively nullifying `otp_hmac` and invitation `token_hash` upon redemption, expiration, invalidation, or delivery failure.
- **Unified Rate Limiting**: Completely removes legacy `LoginRateLimit` and consolidates login IP and account security into the robust `RateLimit` table with sliding windows.
- **Reversible Migrations**: Migration 0051 includes comprehensive forward and rollback pathways, with SQLite table reconstruction correctly handling SQLite's schema limitations.
