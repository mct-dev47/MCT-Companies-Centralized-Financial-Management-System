## Summary
This change removes unused schema and dead code across backend and frontend (`budget` and `cash_inflow` tables/endpoints/schemas, `receivables.expense_id`, and `loan.interest_type`), and adds migration `0068_schema_cleanup_unused_tables_and_columns`. The model, schema, service, router, and frontend cleanups are thorough and consistent, with no dangling imports or callers left behind. However, the SQLite path of migration `0068` crashes with an `OperationalError` on any real pre-existing SQLite database because `receivables.expense_id` carries a `FOREIGN KEY` constraint that SQLite refuses to drop via `ALTER TABLE ... DROP COLUMN`, and the new migration test missed this by creating a synthetic table without the foreign key.

## Blockers
### 🔴 SQLite migration 0068 crashes on existing `receivables.expense_id` foreign key, `backend/app/db/migrations.py:1531-1540`
**Problem**: In `_run_sqlite_migrations`, migration `0068_schema_cleanup_unused_tables_and_columns` drops indexes on `receivables.expense_id` and executes `ALTER TABLE receivables DROP COLUMN expense_id` (`migrations.py:1539`). Prior to this change, `Receivable` defined `expense_id = Column(Integer, ForeignKey("expenses.expense_id", ondelete="SET NULL"), nullable=True, index=True)`, so SQLAlchemy created `receivables` with a table-level `FOREIGN KEY(expense_id) REFERENCES expenses (expense_id) ON DELETE SET NULL` constraint (verified in `backend/mct_financial.db`). SQLite forbids `ALTER TABLE ... DROP COLUMN` on any column referenced in a foreign key definition and raises `sqlite3.OperationalError: error in table receivables after drop column: unknown column "expense_id" in foreign key definition`.
**Why it matters**: Running `run_migrations` against an in-memory clone of `backend/mct_financial.db` fails with this `OperationalError`, and running `test_activity_logs.py` when `engine` binds to `backend/mct_financial.db` fails in `setUpClass`. In `init_db()` (`backend/app/db/session.py:158-161`), the exception is caught and logged as a warning, so migration `0068` rolls back without being recorded in `schema_migrations`, fails to drop `budget`, `cash_inflow`, `receivables.expense_id`, or `loan.interest_type`, and repeats the failure on every application startup while `Receivable` and `Loan` ORM models no longer match the SQLite tables.
**Suggested fix**: Replace `ALTER TABLE receivables DROP COLUMN expense_id` in `_run_sqlite_migrations` with a SQLite table rebuild (like migration `0051` in `backend/app/db/migrations.py:1087-1137`): create `receivables_new` matching the post-0068 `Receivable` schema without `expense_id` or its foreign key, copy existing rows, guard `PRAGMA foreign_keys` (outside an open transaction if needed) so `receivable_payments`'s `ON DELETE CASCADE` FK neither blocks `DROP TABLE receivables` nor deletes child payment rows, rename `receivables_new` to `receivables`, and recreate the non-`expense_id` indexes.

## Major
### 🟠 Migration 0068 test omits the real `FOREIGN KEY`, child rows, and idempotency checks, `backend/tests/test_migrations.py:152-181`
**Problem**: `test_migration_0068_drops_unused_tables_and_columns` seeds a simplified `receivables` table with `(receivable_id, sale_id, expense_id)` and an index, omitting `FOREIGN KEY(expense_id) REFERENCES expenses (expense_id) ON DELETE SET NULL`, omitting `receivable_payments` (`FOREIGN KEY(receivable_id) REFERENCES receivables (receivable_id) ON DELETE CASCADE`), inserting zero rows, and only calling `run_migrations` once.
**Why it matters**: Omitting the foreign key allowed the test to pass while the real SQLite database (`backend/mct_financial.db`) crashes on `0068`. Once `0068` uses a table rebuild, an untested rebuild can silently drop rows or cascade-delete `receivable_payments` if foreign-key enforcement is active during `DROP TABLE receivables`.
**Suggested fix**: Update `test_migration_0068_drops_unused_tables_and_columns` to create `company`, `sales`, `expenses`, `receivables` (with its real foreign keys and indexes), and `receivable_payments`, enable `PRAGMA foreign_keys=ON`, seed sample `receivables` and `receivable_payments` rows, execute `run_migrations` twice to verify idempotency, and assert the obsolete objects are gone while all `receivables` and `receivable_payments` rows remain intact.

## Minor
### 🟡 Standalone Postgres SQL script omits `IF EXISTS` on altered tables, `backend/migrations/0068_schema_cleanup_unused_tables_and_columns.postgres.sql:6-7`
**Problem**: Unlike `backend/app/db/migrations.py:644-653`, which guards `ALTER TABLE` with `to_regclass('public.receivables')` and `to_regclass('public.loan')`, lines 6–7 of the standalone Postgres script run `ALTER TABLE receivables ...` and `ALTER TABLE loan ...` without `IF EXISTS` on the table names (and `backend/schema.sql` does not define `receivables`).
**Why it matters**: Running `0068_schema_cleanup_unused_tables_and_columns.postgres.sql` manually in Supabase SQL Editor against a fresh database provisioned from `schema.sql` will fail with `relation "receivables" does not exist`.
**Suggested fix**: Use `ALTER TABLE IF EXISTS receivables DROP COLUMN IF EXISTS expense_id CASCADE;` and `ALTER TABLE IF EXISTS loan DROP COLUMN IF EXISTS interest_type CASCADE;` in `backend/migrations/0068_schema_cleanup_unused_tables_and_columns.postgres.sql`.
