## Minor

### 🟡 Postgres `0067` has no lock retry loop and `session.py` swallows abort errors, `backend/app/db/migrations.py:604-636`
**Problem**: In `_run_postgresql_migrations`, migration `0067_company_bank_schema_cleanup` runs `ALTER TABLE` statements under `SET LOCAL lock_timeout = '5s'` without a retry loop (unlike `0053` at `lines 348-361` and `0054` at `lines 373-386`). When `0067` raises inside `run_migrations`, the shared transaction rolls back, and `backend/app/db/session.py:158-162` catches the exception with a warning and continues startup.
**Why it matters**: If concurrent production traffic holds locks on `company` or `bank_accounts` longer than 5 seconds during a deploy, the server can still boot while legacy `NOT NULL` columns (`company.starting_balance` and `bank_accounts.account_number`) remain in Postgres, causing `NotNullViolation` failures on subsequent company or bank creation.
**Suggested fix**: Add a bounded retry loop around `0067` matching `0053` and `0054`, and fail fast in production if `0067` fails to complete.

### 🟡 Manual Postgres script drops only `fk_bank_accounts_company_id` by name, `backend/migrations/0067_company_bank_schema_cleanup.postgres.sql:18-23`
**Problem**: Unlike `backend/app/db/migrations.py:620-633`, which checks `pg_constraint` for any existing foreign key on `bank_accounts.company_id`, the standalone SQL file only executes `DROP CONSTRAINT IF EXISTS fk_bank_accounts_company_id` before adding `fk_bank_accounts_company_id`.
**Why it matters**: Running `0067_company_bank_schema_cleanup.postgres.sql` manually in Supabase SQL Editor against a database originally created by `Base.metadata.create_all` (where the constraint may be autogenerated as `bank_accounts_company_id_fkey`) will create a duplicate foreign key constraint.
**Suggested fix**: Check `pg_constraint` inside a `DO` block before adding `fk_bank_accounts_company_id`, or drop any existing foreign key on `bank_accounts.company_id` first.

### 🟡 Unchecked explicit `company_id` causes unhandled `IntegrityError` on bank creation, `backend/app/services/bank_service.py:309-335`
**Problem**: Now that `bank_accounts.company_id` enforces `FOREIGN KEY (company_id) REFERENCES company(company_id) ON DELETE SET NULL`, `BankService.create_account` assigns `resolved_cid = data.company_id` without checking whether that company exists, and `create_bank_account` in `backend/app/api/v1/endpoints/bank_accounts.py:158-173` does not catch `IntegrityError`.
**Why it matters**: Submitting a nonexistent `company_id` to `POST /api/v1/bank-accounts` returns an unhandled HTTP 500 error in Postgres instead of a clean 400 or 404 validation error.
**Suggested fix**: Verify that an explicit `data.company_id` exists in `company` or catch `IntegrityError` in `create_bank_account` and return an explicit client error.
