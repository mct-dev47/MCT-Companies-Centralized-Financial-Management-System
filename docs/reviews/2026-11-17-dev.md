## Summary
This change delivers meaningful backend performance and data-integrity improvements—dropping obsolete tables (`0069`), adding foreign keys and composite sorting indexes (`0070`), batching group/receivable/company queries to remove N+1 patterns, and introducing pagination/summary/export endpoints. However, three blockers prevent merging as-is: an unused local function in `ActivityLogPage.tsx` breaks strict TypeScript compilation (`noUnusedLocals: true`), `CompanyService.delete_company()` omits `daily_remarks` and will hit the new `ON DELETE RESTRICT` foreign key, and six core frontend pages still call unpaginated service methods while the corresponding backend endpoints now cap responses at 50 rows. Several Major RBAC inconsistencies (`owner`/`admin` scope checks), an existing failing test (`test_expenses.py`), missing `X-Total-Count` on `/receivables`, truncated activity-log exports, and untested endpoints also need attention.

## Blockers
### 🔴 Unused local function fails TypeScript `noUnusedLocals` build, `frontend/src/pages/ActivityLogPage.tsx:47`
**Problem**: `parseDateForFilter` (`frontend/src/pages/ActivityLogPage.tsx:47-55`) remained after date-range filtering moved server-side and has zero callers anywhere in `frontend/src/`, while `frontend/tsconfig.json:19` sets `"noUnusedLocals": true`.
**Why it matters**: Strict TypeScript checking (`tsc`) rejects unused local declarations (`TS6133`), breaking frontend typechecking and CI builds.
**Suggested fix**: Delete `parseDateForFilter` from `ActivityLogPage.tsx` and run `tsc --noEmit` across `frontend/` before merge.

### 🔴 `delete_company()` omits `daily_remarks`, failing with FK violation after `0070`, `backend/app/services/company_service.py:501-525`
**Problem**: Migration `0070` (`backend/migrations/0070_foreign_keys_and_index_cleanup.postgres.sql:19-21`, matching `backend/app/models/daily_remark.py:18`) adds `fk_daily_remarks_company_id ... ON DELETE RESTRICT`, while `CompanyService.delete_company()` manually deletes rows from dependent child tables (`lines 501-522`) before deleting the `Company` row (`line 524`) without deleting from `daily_remarks`.
**Why it matters**: Deleting any company that has at least one `daily_remarks` row on PostgreSQL (or FK-enforced SQLite) triggers an `IntegrityError` and returns HTTP 500 via `_database_error("delete company", error)` (`line 534`).
**Suggested fix**: Delete matching `daily_remarks` rows inside `delete_company()` before `self.db.delete(company)`, and add a test covering `delete_company()` with `PRAGMA foreign_keys = ON` and existing `DailyRemark` records.

### 🔴 Backend defaults to `limit=50` while 6 frontend pages still call unpaginated endpoints, `backend/app/core/pagination.py:12`
**Problem**: `GET /sales` (`backend/app/api/v1/endpoints/sales.py:157,219`), `GET /expenses` (`backend/app/api/v1/endpoints/expenses.py:299,349`), `GET /loans` (`backend/app/api/v1/endpoints/loans.py:419,515`), `GET /bills` (`backend/app/api/v1/endpoints/bills.py:68,82-83`), and `GET /receivables` (`backend/app/api/v1/endpoints/receivables.py:64,82-83`) now apply `PaginationParams` (`default=50`, `le=100`). Although new `*Paginated`/`Summary`/`Export` service methods were added to `frontend/src/services/`, zero pages call them; `SalesPage.tsx:618`, `ExpensePage.tsx:337`, `LoanPage.tsx:361`, `BillsPage.tsx:208`, `receivablesStore.ts:123`, and `TransactionPage.tsx:969-971` still call the unpaginated methods with no `page`/`limit`.
**Why it matters**: Any company or consolidated view with more than 50 records in sales, expenses, loans, bills, or receivables silently receives only the first 50 rows, causing incomplete tables, wrong client-computed KPI cards, broken searches, and incomplete exports without raising an error.
**Suggested fix**: Wire `SalesPage`, `ExpensePage`, `LoanPage`, `BillsPage`, `ReceivablesPage`/`receivablesStore`, and `TransactionPage` to the server-side paginated + summary/export APIs (including server-side filter/page changes), or keep the unpaginated callers compatible until each page migration lands.

## Major
### 🟠 Inconsistent `is_privileged` checks exclude `owner` (and `admin` on Sales/Loans), `backend/app/api/v1/endpoints/sales.py:277`
**Problem**: `backend/app/core/dependencies.py:319,346` (`check_company_access`, `get_authorized_company_scope`) and `backend/app/api/v1/endpoints/bank_accounts.py:84` grant group-wide read access to `"admin"`, `"audit"`, `"auditor"`, `"owner"`, and `is_admin=True`. In contrast, `_build_sales_query` (`sales.py:277`) and `get_loans` (`loans.py:427`) restrict `is_privileged` to `("audit", "auditor")`, and `_build_expenses_query` (`expenses.py:198`) omits `"owner"`. Additionally, when `resolve_company` raises a non-`HTTPException` at `sales.py:303-304`, the fallback filters by `Company.company_name` without restricting `Sale.company_id.in_(user_company_ids)` for non-privileged users (unlike `expenses.py:224-227`).
**Why it matters**: An `owner` account (or an `admin` account on `/sales` and `/loans`) without explicit `company_ids` receives `[]` and zeroed KPIs (masked in `test_db_optimization_and_pagination.py:165` only because the fixture manually passes `company_ids=[c1, c2]` on `admin_user`), and the fallback branch in `sales.py:304` risks bypassing company scoping.
**Suggested fix**: Derive company scope uniformly via `get_authorized_company_scope` (including `admin`, `audit`, `auditor`, and `owner`) in `sales.py`, `expenses.py`, and `loans.py`, and restrict the fallback branch at `sales.py:304` to `user_company_ids`.

### 🟠 Sales summary math skew on partial receivables and ignored `status` param on daily summaries, `backend/app/api/v1/endpoints/sales.py:438-441,494`

**Suggested fix**: Partition `paid_d` vs `max(Decimal("0.00"), amt_d - paid_d)` cleanly in `get_sales_summary`, and either apply `status` in both daily-summary builders or remove the unused query parameter.

## Minor
### 🟡 Falsy-zero bug and premature header read when parsing `X-Total-Count`, `frontend/src/services/employeeService.ts:293,321-328`
**Problem**: All new `*Paginated` service helpers (`employeeService.ts:293,328`, `activityLogService.ts:202`, `billsService.ts:430`, `receivablesService.ts:119`, etc.) evaluate `totalHeader !== null ? Number(totalHeader) || items.length : items.length`. Because `0` is falsy in JavaScript, a header value of `"0"` or an unparseable string falls back to `items.length`. In `employeeService.getCompaniesPaginated` (`lines 321-328`), `response.headers.get('X-Total-Count')` is also read before `mapApiResponse` validates `response.ok` (unlike `getUsersPaginated` at `lines 286-288`).
**Why it matters**: Non-finite headers or inconsistent zero totals produce wrong page counts, and failed responses in `getCompaniesPaginated` parse headers before throwing.
**Suggested fix**: Check `if (!response.ok)` first, then parse with `const parsed = totalHeader !== null ? Number(totalHeader) : NaN; const total = Number.isFinite(parsed) && parsed >= 0 ? parsed : items.length`.

### 🟡 `EmployeePage` header count, search field mismatch, and dual-fetch race on filter changes, `frontend/src/pages/EmployeePage.tsx:83-89,114-115,173,210`
**Problem**: `EmployeePage.tsx:173` renders `{companies.length} companies registered in MCT Group` (the current page slice) instead of `{totalCompanies}`. Its search placeholder (`line 210`) and client filter (`lines 114-115`) promise `contactNumber`/`telephoneNumber` search while `backend/app/api/v1/endpoints/companies.py:111-115` searches only `name` and `location`. In both `EmployeePage` (`lines 83-89`) and `UserManagementPage` (`lines 91-97`), resetting `currentPage` to `1` in a separate `useEffect([searchQuery, sortBy])` causes `loadData` to fetch once with the stale `currentPage` and then again for page `1`, with no search debounce or stale-response cancellation.
**Why it matters**: Typing in the search bar triggers rapid back-to-back API requests per keystroke that can resolve out of order, and header totals/contact searches mislead admins.
**Suggested fix**: Show `totalCompanies`, align backend search fields or UI copy, debounce `searchQuery`, and reset `currentPage` directly inside filter handlers (with `AbortController` or a request sequence check).

### 🟡 `SaleOut` and `_expense_to_out` omit `bank_account_id`, `backend/app/api/v1/endpoints/sales.py:222-240,365-383`
**Problem**: Both `SaleOut` (`backend/app/schemas/sale.py:270`) and `ExpenseOut` (`backend/app/schemas/expense.py:171`) declare `bank_account_id: Optional[str] = None`, and `_build_sales_query`/`_build_expenses_query` filter by `bank_account_id`, yet `get_sales`/`export_sales` (`sales.py:222-240,365-383`) and `_expense_to_out` (`expenses.py:262-283`) do not pass `bank_account_id`.
**Why it matters**: Serialized sales and expense rows always return `bank_account_id: null` on list/export responses.
**Suggested fix**: Include `bank_account_id=sale.bank_account_id` in `SaleOut` and `bank_account_id=exp.bank_account_id` in `_expense_to_out`.

### 🟡 Single-string multi-statement execution in PostgreSQL migration `0070`, `backend/app/db/migrations.py:698`
**Problem**: `0066` (`line 668`) and `0069` (`line 683`) iterate `_sql_statements(...)`, whereas `line 698` passes the entire `0070_foreign_keys_and_index_cleanup.postgres.sql` file (containing `DROP INDEX`, a `DO $$ ... END $$;` block, and six `CREATE INDEX` statements) to a single `conn.execute(text(...))`.
**Why it matters**: While `_sql_statements` isn't dollar-quote safe for `DO $$ ... $$`, sending multiple DDL statements in one `conn.execute()` call depends on DBAPI drivers permitting multi-statement execution (for instance, `psycopg` v3 rejects multi-statement prepared `execute`, whereas separate discrete calls work across drivers).
**Suggested fix**: Teach `_sql_statements` to respect `$$` dollar-quoted blocks or execute the `DROP INDEX`, `DO $$ ... $$`, and `CREATE INDEX` sections as separate statements.
