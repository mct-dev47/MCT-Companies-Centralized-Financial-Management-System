## Summary
This change implements Spec 0044, introducing frontend HTTP security headers (CSP, HSTS, frame options), compound indexes for high-frequency database tables, pagination parameters with response headers for legacy `/bills` and `/loans` endpoints, and a GitHub Actions database backup workflow. The security headers and compound query indexes are well-conceived and align well with system performance and security goals. However, the change cannot merge in its current state due to critical flaws in the backup workflow (the S3 upload step condition silently evaluates to false, and the unencrypted production database dump is exposed as a GitHub Actions artifact), loan endpoint cache hits omitting pagination headers, an invalid GitHub Actions expression breaking AWS region resolution, and broken DDL in `backend/schema.sql`.

## Blockers
### 🔴 GitHub Actions Step Condition Bug Prevents S3 Backup, `.github/workflows/database-backup.yml:46`
**Problem**: The upload step condition `if: env.AWS_ACCESS_KEY_ID != '' && env.BACKUP_BUCKET_NAME != ''` attempts to read `env.` variables declared inside that same step's `env:` block. In GitHub Actions, a step's `if` condition is evaluated before step-level `env` variables are loaded and can only access workflow- or job-level `env` contexts. As a result, `env.AWS_ACCESS_KEY_ID` evaluates to an empty string (`''`), the condition evaluates to `false`, and the backup upload to S3/Cloudflare R2 is silently skipped on every scheduled and manual run.
**Why it matters**: The automated off-site database backup will never be transferred to cloud object storage (S3/R2), completely breaking disaster recovery and off-site backup archiving in production without raising any failure alarm in the workflow run.
**Suggested fix**: Evaluate the secrets directly in the step condition (`if: secrets.AWS_ACCESS_KEY_ID != '' && secrets.BACKUP_BUCKET_NAME != ''`), declare `env` at the job level (`jobs.database-backup.env`), or perform the configuration check inside the bash script (`run: | if [ -n "$AWS_ACCESS_KEY_ID" ] ...`).

### 🔴 Unencrypted Production Database Dump Exposed as GitHub Artifact, `.github/workflows/database-backup.yml:66`
**Problem**: Step "Retain Backup Artifact in GitHub Actions" uploads `backups/*.dump` directly to GitHub Actions build artifacts with 7-day retention (`uses: actions/upload-artifact@v4`). This dump contains plaintext production database contents—including user credentials, audit trails, company financial statements, bank accounts, and loans. Spec 0044 explicitly states: "Encrypt the dump file before uploading to AWS S3 / Cloudflare R2 / Google Cloud Storage."
**Why it matters**: GitHub Actions artifacts can be downloaded by anyone with read access to the GitHub repository. Exposing raw production financial database dumps in GitHub Actions storage violates data protection principles and contradicts the encryption requirement specified in Spec 0044.
**Suggested fix**: Encrypt the dump with GPG/AES (e.g. `gpg --symmetric --cipher-algo AES256 --passphrase "$BACKUP_ENCRYPTION_KEY"`) before uploading, or remove the unencrypted artifact upload step entirely if off-site object storage (S3/R2) is used.

## Major
### 🟠 Cache Hit in `get_loans` Omits Pagination Response Headers, `backend/app/api/v1/endpoints/loans.py:406`
**Problem**: In `backend/app/api/v1/endpoints/loans.py`, `get_loans` checks `cached = system_cache.get(cache_key)`. When a cached list of loans is found, it immediately returns `cached`. The response headers `X-Total-Count`, `X-Page-Limit`, and `X-Page-Offset` are populated only downstream after database/Supabase queries.
**Why it matters**: On any cache hit (within the 60-second TTL), the API client receives the loan items but `X-Total-Count`, `X-Page-Limit`, and `X-Page-Offset` headers are missing. Clients relying on these headers for pagination controls (such as calculating total pages) will see the headers disappear on repeated calls or page navigation.
**Suggested fix**: Store both `items` and `total_count` in the cache tuple `(result, total_count)` and ensure `response.headers["X-Total-Count"] = str(total_count)` (as well as `X-Page-Limit` and `X-Page-Offset`) is set unconditionally before returning, even on cache hits.

### 🟠 Invalid GitHub Actions Expression Syntax for Region Fallback, `.github/workflows/database-backup.yml:50`
**Problem**: `AWS_DEFAULT_REGION: ${{ secrets.AWS_DEFAULT_REGION || 'ap-southeast-1' }}` uses JavaScript-style logical OR coalescing. In GitHub Actions workflow expressions, `||` is a boolean logical operator that returns `true` or `false`, not the right-hand string literal. When `secrets.AWS_DEFAULT_REGION` is unset, this expression evaluates to `true`, setting the environment variable `AWS_DEFAULT_REGION="true"`.
**Why it matters**: AWS CLI commands like `aws s3 cp` will receive `--region true` or `AWS_DEFAULT_REGION=true`, resulting in an invalid region format error and failing the S3 upload.
**Suggested fix**: Pass `AWS_DEFAULT_REGION: ${{ secrets.AWS_DEFAULT_REGION }}` and use standard POSIX parameter expansion in the run script: `REGION="${AWS_DEFAULT_REGION:-ap-southeast-1}"`.

### 🟠 `backend/schema.sql` Contains Broken Index DDL on Missing Columns/Tables, `backend/schema.sql:237`
**Problem**: The compound indexes added to the bottom of `backend/schema.sql` reference `sales.deposit_status` (line 237) and table `bank_transactions` (line 239). However, `backend/schema.sql` does not include `deposit_status` in the `sales` table definition (line 77), nor does it declare the `bank_transactions` table anywhere in the file.
**Why it matters**: Anyone executing `backend/schema.sql` to initialize a staging or development database from scratch will encounter SQL execution errors (`column "deposit_status" does not exist` and `relation "bank_transactions" does not exist`).
**Suggested fix**: Update the `sales` table definition in `schema.sql` to include `deposit_status` (and other baseline migration columns like `deposit_date`), and add the `bank_accounts` and `bank_transactions` table definitions before creating indexes on them.

### 🟡 Empty List `company_ids=[]` Bypasses Filtering, `backend/app/services/bills_service.py:332`
**Problem**: In `BillsService.count_bills` and `list_bills`, the check is written as `elif company_ids:`. If an empty list `[]` is passed (e.g., when a user has no assigned companies), `bool([])` evaluates to `False`, bypassing the filter entirely and counting/listing all bills.
**Why it matters**: While `_resolve_caller_scope` currently raises 403 earlier if no companies are assigned, defensive service methods should check `elif company_ids is not None:` and filter with `Bill.company_id.in_(company_ids)` to avoid accidental full-table scans or leakage if called from other contexts.
**Suggested fix**: Change `elif company_ids:` to `elif company_ids is not None:`.
